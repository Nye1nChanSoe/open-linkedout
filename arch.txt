::Scheduler
Scheduler should own the ordering rather than hard-coded it into scraper

1. Select Eligible search run task
2. Open or resue an authenticated browser session
3. Navigate to its keyword-location search
4. Scrape one page
5. Save results transactionally
6. Schedule the next page after a cooldown
7. Release the worker
8. Select another eligible task

This is all for much better interruption handling.
Persist scraped job after every page is the mental model.

Cooldown or sleep() is part of the scheduler's job not scraper's.

Scraper:
"Page 1 completed"

Application:
"Persist the results and set nextEligibleAt"

Worker:
"Nothing is eligible yet. Remains idle"

::Job Discovery
A discovery record answers 
- Where did we find this job?
- Under which keyword?
- In which location search?
- On which page?
- At what position?
- When?

This is a histroy to keep track of how we discovered that job over time
  means after every campaign, every search keywords etc...
Discovery frequency itself can be a ranking signal. externalJobId

What happens after one page is scraped? by SearchPageTask
1. Normalize the external job id
2. Normalize the canonical URL
3. Check whether the canonical job exists
4. Insert of update the canonical job.
5. Create a discovery record
6. Update page-task counters.
7. Decide whether another page task should be created.

It should ideally happen inside one DB transaction.
